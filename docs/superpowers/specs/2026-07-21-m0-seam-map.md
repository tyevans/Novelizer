## Comparison: canon_fs vs. kg_store/kg_projector

Both projection stacks recompute a fresh view from canon, keyed to what triggered the recompute — but they differ in *when* that recompute happens and *what* it's keyed on:

- **canon_fs is pull/on-demand, keyed on the request.** `CanonBackend._snapshot` (backend.py:93-110) rebuilds a full `_Snapshot` — six record-kind dicts plus `build_path_index` and the knowledge matrix — synchronously inside every `aread`/`als`/`aglob`/`agrep` call. There is no persisted cache: each backend call is its own consistent-but-throwaway view, and `CanonBackend._render` (backend.py:112-127) dispatches by `kind` string to the fiction-only `render_*` functions in `canon_fs/render.py` to turn one record into text on the spot.
- **kg_store/kg_projector is push/event-driven, keyed on the event.** `KGProjector.catch_up` (kg_projector.py:59-76) is a cursor-driven consumer over `EventStore` (persisted cursor file, `_load_cursor`/`_save_cursor`), processing each new event through `_index_one` → `_index_character`/`_index_world_entry`/`_index_chapter`, and persisting the resulting entities/relations into `world.db` via `KGStore.upsert_entity`/`upsert_relation` (kg_store.py:61-102) plus `KGStore.link_mention`/`link_relation_mention` (kg_store.py:104-136) — a durable, incrementally-updated projection, not a per-call recompute.
- **The "keyed to what triggered it" idea shows up as two different keys.** canon_fs has no explicit trigger key at all — its snapshot is implicitly keyed on "this call happened now." kg_store makes the trigger explicit as `event_fingerprint` (e.g. `f"chapter:{chapter_id}"` at kg_projector.py:108): `KGStore.clear_mentions_for_fingerprint`/`clear_relation_mentions_for_fingerprint` (kg_store.py:112-122, 138-148) let `KGProjector._index_chapter` (kg_projector.py:104-154) retract exactly the facts a prior version of one source (one chapter revision) contributed, before re-extracting — the reflow pattern. canon_fs has no analogous retraction concept because it never persists a prior render to invalidate; every call already starts from current data.
- **Both split into a generic carrier + fiction-specific producer.** canon_fs's carrier is the rendered markdown string itself, produced by fiction-only functions (`render_chapter`, `render_character`, etc. in `render.py`; `render_blueprint`, `render_ledger`, etc. in `outline_render.py`). kg_store/kg_projector's carrier is `EntityFact`/`RelationFact` (kg_structured.py:6-20), a domain-neutral dataclass pair, produced by fiction-only functions `facts_from_character`/`facts_from_world_entry` (kg_structured.py:23-55) for the structured path, or by the fiction-specific `kg_extraction_prompt` LLM call (kg_projector.py:163, `_extract_chapter_facts`) for the prose-extraction path. In both stacks, the generic-as-is store/backend layer (`KGStore`, `CanonBackend`'s protocol dispatch) never itself names a fiction entity type as a literal; the fiction vocabulary enters only through the producer functions and the hardcoded dispatch tables (`KIND_DIRS`, `INDEXED_EVENT_TYPES`, `_index_one`'s `if` chain) that route to them.
- **Both dispatch tables are the same kind of seam.** `CanonBackend._render`'s `if kind == "chapter": render_chapter(...)` chain (backend.py:112-127) and `KGProjector._index_one`'s `if event_type in (EventType.CHARACTER_CREATED, ...): ...` chain (kg_projector.py:78-84) are structurally identical: a hardcoded string/enum-keyed if-chain routing to a fiction-only handler function. A generalized substrate would replace both with an injected `dict[str, Handler]` supplied by the domain, rather than importing named fiction functions/constants directly.

### Correcting the "not event-sourced" claim

The spec's premise — that deepagents supplies the agent loop, sub-agent delegation, and `BackendProtocol`/`CompositeBackend`, but *not* event-sourcing — is confirmed, with one precision added: it is not merely that deepagents omits event-sourcing as an oversight, its shipped backends are actively structured the *opposite* way. `BackendProtocol` (protocol.py:329-395) defines `write`/`edit` as in-place, current-state mutating operations (`WriteResult`/`EditResult` carry only a resulting `path`/`error`, no revision or event id), with no append-only log, no version history, and no replay/projection concept anywhere in `protocol.py` or `utils.py`. The one shipped backend Novelizer actually wires in (`StateBackend`, `backends/state.py:1,36-46`) is explicitly documented as ephemeral, LangGraph-state-backed storage ("Files persist within a conversation thread but not across threads") — checkpointed by LangGraph for resumability within a run, which is a durability mechanism, not an event-sourced audit log (no `EventStore`-style append-only sequence, no projector, no read-model rebuild from history). `CompositeBackend` (composite.py) is purely a path-prefix router over other `BackendProtocol` instances; it adds no persistence semantics of its own. Novelizer's own `EventStore`/`Projector`/`ReadStore` (canon core, documented earlier in this doc) is therefore entirely home-grown — deepagents contributes the agent-facing file-tool surface and ephemeral/session state, while all event-sourcing, durable canon history, and read-model projection is Novelizer-specific code with no deepagents equivalent.
