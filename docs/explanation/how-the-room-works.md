# How the room works

This document explains the architecture of Novelizer's "room" — the autonomous multi-agent writers' room that drafts a novel while you watch, steer, or walk away. It is an explanation in the [Diataxis](https://diataxis.fr/) sense: it exists to build understanding, not to teach you a first session (that is the [tutorial](../tutorial/first-story.md)) or to enumerate every command and knob (that is the [CLI reference](../reference/novelizer-cli.md) and the [configuration reference](../reference/configuration.md)). Read it when you want to know *why* the system is shaped the way it is: why ten agents share one append-only event log instead of calling each other, why nothing an agent writes becomes canon except through a single gated commit seam, and why the scheduler is a plain cadence-and-readiness loop rather than a workflow engine.

The short version: the room is an event-sourced blackboard system. Agents never talk to each other; they read the shared event log, do their work, and declare intents that a committer either appends to the log or converts into proposals for human review, depending on the current autonomy level. Everything else in this document is a consequence of that one design commitment.

This document covers the `novelizer` bounded context only — the room owns its own event store, agents, and scheduler. For how `novelizer` relates to the repository's other root packages (`substrate`, `tui_kit`, `research_domain`) and why the import boundaries between them are drawn where they are, see [Architecture boundaries](architecture-boundaries.md).

## The room in one paragraph

Ten specialist agents — World Architect, Character Keeper, Muse, Plotter, Author, Editor, Continuity Checker, Retconner, Structure Analyst, and Triage — share a single append-only event log (a SQLite `events` table) that holds everything the story is: worldbuilding, characters, plot beats, prose, edits, retcons. A scheduler ticks about once a second and, whenever a dispatch-pool slot is free (two agents may run concurrently by default), picks the highest-scoring agent from those whose per-agent interval has elapsed, whose self-reported readiness score is above zero, and who are not paused — so an agent runs only when its own cadence and the current state of the log say it has something worth doing. When an agent runs, it reads the log, does its work with an LLM, and hands the result to a single committer seam rather than writing anywhere itself; depending on the room's autonomy level (`full_auto` through `gated_all`, globally or per agent), that committer either appends the event to the log — making it canon that every other agent will see on its next turn — or records it as a proposal that waits for a human to approve or reject. No agent ever calls, messages, or even knows about another agent: coordination happens entirely through what the log contains, and control happens entirely at the commit gate and the scheduler's knobs. The rest of this document unpacks each clause of that paragraph.

## Why a room instead of a pipeline

The obvious way to build a novel-writing system is a pipeline: worldbuild, then plot, then draft, then edit, then check continuity, each stage consuming the previous stage's output and handing a finished artifact to the next. Novelizer deliberately does not work this way, and the reason is that novel-writing is not a monotonic process. A pipeline assumes each stage's output is *done* when the next stage starts. In practice, chapter twelve reveals that the magic system sketched in week one doesn't hold together; a contradiction between two chapters only becomes visible once both exist; a plot thread planted early needs its payoff renegotiated after the middle of the book drifts somewhere unexpected. In a pipeline, all of that is an exception — work flowing backwards against the arrows. In the room, it is just Tuesday: two of the ten agents (Continuity Checker and Retconner) exist *only* to look backwards at canon that earlier turns already produced, and the Editor routinely sends prose the Author considered finished back for a targeted rewrite. Revision is a permanent, first-class activity, not a stage.

The room model replaces "what stage are we in?" with "who has something worth doing right now?" — and crucially, each agent answers that question for itself, by reading the log. The Editor's `readiness()` scores itself by how many draft chapters are waiting (`min(1.0, drafts / 3)` in `novelizer/agents/editor.py`); the Continuity Checker scores itself down as open contradiction flags pile up, throttling itself rather than flooding the room with findings nobody has resolved yet (`novelizer/agents/continuity_checker.py`). There is no central plan that knows the Editor should run next — the state of the story itself is the plan. The one nod to sequence is the registry ordering in `novelizer/agents/registry.py`, which puts the planner (Plotter) ahead of the writer (Author) so a fresh, empty room bootstraps sensibly; after the first few events exist, readiness scores dominate and the order is emergent.

This buys several properties a pipeline cannot offer:

- **Failure is local.** When an agent's run raises, the scheduler records the error, consumes the agent's interval anyway so it backs off instead of hot-looping, and moves on (`Scheduler._run` in `agent_kit/scheduler.py`). A run killed by endpoint saturation backs off harder still — three intervals, not one (`note_rate_limited` in `agent_kit/base.py`) — so a rate-limited fleet drains rather than piles back on. The other nine agents never notice. In a pipeline, a crashed stage stalls everything downstream.
- **Idleness is cheap.** An agent that runs, looks at the log, and decides there is nothing to do steps back for three intervals instead of one (`note_pass` / `PASS_BACKOFF_MULTIPLIER` in `novelizer/agents/base.py`), and watermark fingerprints let an agent report readiness zero until the story state it cares about actually changes. A pipeline has to *invent* work for every stage on every pass or build explicit skip logic.
- **Steering is continuous, not between-stages.** You can pause any agent (or all of them) at any moment, and a director override signal makes the scheduler dispatch a specific agent ahead of the readiness ranking on its next tick (`SignalKind.override` handling in `Scheduler.tick`). There is no "wait for the current phase to finish" — because there are no phases.
- **The roster is open.** Adding an agent means adding a spec to `AGENT_REGISTRY` and teaching it to read the log and declare intents. No existing agent's inputs or outputs change, because no agent has inputs or outputs wired to another agent — a pipeline would require re-plumbing the handoffs on either side of the insertion point.

The cost of giving up the pipeline is giving up its guarantees: nothing ensures the world is "finished" before drafting starts, and nothing prevents two agents from acting on the same state concurrently in ways a fixed sequence would have serialized. The room accepts both and compensates elsewhere — the append-only log means concurrent work adds events rather than overwriting anything, and the gated commit path means a human can stand at the one place where anything becomes canon. Those compensations are the subject of the next two major sections, and the [Alternatives considered](#alternatives-considered) section returns to the pipeline (and other rejected shapes) with the full picture in hand.

## The event log is the only shared surface

Physically, the log is one SQLite table. `novelizer/canon/event_store.py` creates it — `sequence` (an autoincrementing integer primary key), a UUID `id`, an `event_type` string, an `aggregate_id`, a JSON `payload`, a `created_at` timestamp, and a `run_id` tying the event to the agent run that produced it — and the `EventStore` class wrapped around it exposes exactly two kinds of operation: append (`append` / `append_raw`) and ordered read (`events_since`, `events_tail`, `events_for_aggregate`, `events_for_run`). There is no update method and no delete method, not as a convention but as an absence: no code path in the system can modify or remove a row once it exists. Concurrent appends from the dispatch pool are serialized by an asyncio write lock inside the store, so the `sequence` column is a total order over everything that has ever happened in the room — event *N+1* was appended by something that could have seen events *1..N*.

"Only shared surface" is two claims, and both are load-bearing. The first is that everything the agents share goes through the log. The event vocabulary in `novelizer/canon/events.py` — around sixty types — covers not just the obvious narrative facts (`chapter.created`, `character.updated`, `thread.planted`, `secret.revealed`) but the room's planning artifacts (`chapter_brief.drafted`, `blueprint.adopted`, `arc.declared`), its self-critique (`flag.created`, `flag.escalated`), its governance (`proposal.created`, `proposal.approved`, `autonomy.changed`), the human's steering (`director_signal.created`), and even the chat between the Director and an agent (`chat.user_messaged`, `chat.agent_replied`). Replaying the log reproduces not only the novel but the decisions, vetoes, and conversations around it. The second claim is that nothing else is shared: there is no message bus, no shared scratch memory, no agent-to-agent call. If the Author needs to know what the Plotter planned, the only place that plan can exist is a `chapter_brief.drafted` event; there is no side channel for it to have traveled through. That is what makes the coordination story ([Coordination without messages](#coordination-without-messages), below) tractable to reason about — the log's contents at sequence *N* are, exactly and exhaustively, the shared state of the room.

Append-only forces a particular grammar onto change: corrections are new facts, not edits to old ones. A rewritten chapter is a `chapter.revised` event citing the chapter's id; a worldbuilding entry that no longer holds is `world_entry.superseded`; a paid-off plot thread is `thread.paid_off`. The old prose, the old entry, and the planted thread all remain in the log forever — what changes is the *current* view derived from them. That derived view is the job of the `Projector` (`novelizer/canon/projector.py`), which folds each event, in sequence order, into ordinary queryable tables — `chapters`, `characters`, `threads`, `promises`, `secrets`, `arcs`, and the rest — tracking its position in a `projector_state` row, while `ReadStore` (`novelizer/canon/read_store.py`) serves reads from those tables. This is the standard event-sourcing split: the log is the truth, the projections are a disposable cache of it (the Projector's `_reset_state` helper empties every projection table and resets the sequence cursor to zero, and the next `catch_up` rebuilds them by replaying the whole log). The projector's own comments state the doctrine at its sharpest — when a revision arrives whose prose is suspiciously long, it logs a warning and commits anyway: "event sourcing: the log is the truth, a length anomaly is a signal to notice via the feed, not something to silently correct."

Because bad or stale events cannot be deleted, the projection rules are where the log's discipline lives. Ids are minted exactly once — a second `thread.planted` for an existing id is a projection no-op, never a reset ("first-plant-wins"). Terminal states are absorbing — touching a thread that was already paid off, or progressing a promise that was already released, leaves the projection untouched. Events citing unknown ids project to nothing rather than raising. In every case the event stays in the log as a fact about what some agent claimed, while the derived state stays coherent. A few event types are deliberately never projected at all: `agent.remarked` (an agent's in-personality feed line) and `chapter.mined` (a bookkeeping marker) are appended for the record and for idempotency but have no `_apply` branch, by design. The same append-only stance governs schema evolution: old logs are never rewritten. New payload fields are added with defaults so that, as the field docstrings in `events.py` put it, "events written before this field replay unchanged"; retired event types like the legacy `retcon_request.*` family keep a projection branch that aliases them into the modern `flags` table so pre-Flag logs keep working; and the only migration the events table itself has ever needed was additive (a nullable `run_id` column).

The log's total order is also what several other mechanisms in this document quietly stand on. Agent watermarks (see [Intervals, pass backoff, and watermarks](#intervals-pass-backoff-and-watermarks)) work because "has anything I care about changed?" reduces to comparing fingerprints of state derived from a strictly growing sequence. The Muse's `inspiration.drawn` event records the PRNG seed it drew with, so replaying the log reproduces the exact hand — the log is deterministic history, not merely an audit trail. And the room's operational telemetry reuses the same `EventStore` machinery pointed at a second, separate database file (`telemetry.db`, wired in `novelizer/runtime.py`), keeping instrumentation out of canon while `run_id` lets you join the two after the fact: for any event in the story, you can find the agent run that produced it.

The original rationale for choosing this design — including the alternatives weighed at the time — is preserved as a historical design record in [the event-sourced store design spec](../superpowers/specs/2026-06-19-event-sourced-store-design.md). What the log deliberately does *not* give you is any control over what gets appended: `EventStore.append` will happily record anything it is handed. That control lives one layer up, at the committer seam — the subject of [The gated commit path](#the-gated-commit-path).

## The ten-agent fleet and its scheduling order

The roster is declared in exactly one place: `AGENT_REGISTRY` in `novelizer/agents/registry.py`, a ten-element list of `AgentSpec`s. Each spec carries the agent's name, its tool and subagent grants (each keyed to a per-agent settings flag such as `editor_tools_enabled` — see the [per-agent flags in the configuration reference](../reference/configuration.md#per-agent-tool-enablement-flags)), and a `construct` function that builds the agent from a shared `AgentContext` (read store, committer, event store, settings, voice-pack personality). `Runtime` iterates the registry to construct every agent, and hands the resulting list — in registry order — to the scheduler. Adding an eleventh agent is one new module plus one new list entry; nothing else in the room changes.

The ten, in registry order, with what each one is for and when it asks to run:

| Agent | Role | Default cadence | Readiness: "I want to run when…" |
|---|---|---|---|
| **World Architect** | Grows the world's lore — geography, factions, history, systems — additively, never contradicting existing canon. | 120 s (`default_agent_interval`) | The world is thin: score is `max(0.2, 1.0 − entries/50)`, watermark-gated on chapter movement. A pending director seed forces 1.0 unconditionally. |
| **Character Keeper** | Maintains the canonical cast: discovers characters the prose introduces, keeps sheets true to recent chapters, records who knows which secrets. | 120 s (`default_agent_interval`) | Chapters exist but the cast is empty — bootstrapping the cast scores 0.8, because nothing else mints characters. Otherwise a modest steady score (0.5 or 0.2), watermark-gated. |
| **Muse** | The one agent with no LLM: deals seeded hands of corpus draws (names, professions, settings, beats) as `inspiration.drawn` events. | 60 s (`muse_interval`) | No unconsumed hand is on the table (0.9); zero while one is waiting. The Author consumes the hand at chapter commit, which flips readiness back on. |
| **Plotter** | The showrunner: proposes a story blueprint when none exists, keeps 1–3 chapter briefs drafted ahead of the Author, judges beat fulfillment, plans resolutions. Writes no prose. | 240 s (`plotter_interval`) | Zero in a completely empty room; 1.0 the moment chapters exist with no blueprint; otherwise scales with how short the brief runway ahead of the Author is, bumped to ≥0.9 when a blueprint beat is running late. |
| **Author** | The fleet's only prose writer. Drafts each new chapter; every other agent advises through structured notes and never writes prose. | 300 s (`author_interval`) | Few unedited drafts are queued: `1.0 − drafts/3`, hitting zero once three drafts await the Editor. |
| **Editor** | A judge, not a writer: decides whether a drafted chapter ships or goes back to the Author for one targeted rewrite, and records what the finished prose establishes. | 120 s (`default_agent_interval`) | Drafts are waiting: `min(1.0, drafts/3)` — the exact mirror of the Author's score. |
| **Continuity Checker** | Finds contradictions in canon and files them as flags; also runs the prose-mining pass that extracts on-page facts the log has no event for. Repairs nothing. | 900 s (`continuity_interval`) | Its own backlog is small: `max(0.1, 1.0 − open_contradictions/5)`, watermark-gated — it throttles itself down as unresolved findings pile up. |
| **Retconner** | Surgical canon repair: verifies a filed contradiction still exists in live canon and resolves it with the smallest amendment that removes it. | 120 s (`default_agent_interval`) | Contradiction flags are open: `min(1.0, open_flags/3)` — it ramps up exactly as the Checker throttles down. |
| **Structure Analyst** | A judge of shape: assigns each chapter one tension score and one pacing label. No prose, no flags, no thread management. | 180 s (`structure_analyst_interval`) | Recent chapters are unscored: `min(1.0, unscored/3)`, zero when everything is scored. |
| **Triage** | The meta-agent: reads every open flag any other agent filed, in any category, and decides whether it is a real issue worth keeping open. | 120 s (`triage_interval`) | Any flags are open: `min(1.0, open_flags/3)`. |

Three design decisions are visible in that table. First, **exactly one agent writes prose**. The Author owns the sentences; the Editor, Structure Analyst, and Continuity Checker are explicitly framed as judges or extractors in their own system prompts ("You are a JUDGE, not a writer"), and the Plotter's opens with "You do not write prose." This is a deliberate division between generating and evaluating: a critic that can rewrite what it criticizes tends to drift into doing the Author's job badly, so the critics' only outputs are structured judgments — approvals, scores, briefs, flags — that flow back to the Author through the log. Second, the fleet contains its own immune system: the Checker files problems, the Retconner fixes one kind of problem (contradictions), and Triage audits the problem queue itself, dismissing flags that are not real issues so the Checker's `1.0 − open/5` throttle does not strangle it on false positives. Third, readiness scores are designed in *pairs of opposing pressures*. The Author's `1.0 − drafts/3` and the Editor's `drafts/3` form a see-saw around the draft queue — as unedited chapters accumulate, the Author quiets down and the Editor wakes up, and the queue self-regulates around a depth of about three without any component enforcing that number. The Checker and Retconner form the same see-saw around the contradiction queue. No agent knows its counterpart exists; the balance emerges from two functions reading the same projection.

The registry's list order is the *scheduling order*, and it is worth being precise about how little that means. The scheduler (next section) ranks eligible agents by readiness score, descending, and dispatches from the top — so almost all of the time, who runs next is decided by the scores, not the list. The list order matters only as the tie-break: Python's sort is stable, so among agents with equal scores, the one earlier in the registry wins the dispatch slot. The registry's own comment records the one tie the ordering is there to break — "the planner (plotter) ticks before the writer (author) in a fresh room." Early in a story, both the Plotter (no blueprint, no briefs) and the Author (no drafts) report full urgency; putting the Plotter immediately ahead of the Author in the list means that when they tie at 1.0, the room plans before it drafts. The broader shape of the list follows the same logic as a courtesy to the bootstrap phase — world and cast suppliers first (World Architect, Character Keeper, Muse), then planner, then writer, then the critics and repair crew (Editor, Continuity Checker, Retconner, Structure Analyst), with Triage last — but after the first few events exist, readiness scores diverge and the ordering recedes into irrelevance. It is a preference for the opening move, not a pipeline in disguise.

The cadence column is the other half of each agent's scheduling identity, and the defaults encode a cost-and-urgency judgment rather than a rhythm. The Muse is cheapest (no LLM call) and gates the Author's raw material, so it polls fastest at 60 seconds. The mid-tier agents sit at the 120-second `default_agent_interval`. The Author's 300 seconds reflects that drafting a chapter is the single most expensive LLM call in the room — and that there is no point asking more often than the Editor can clear the queue. The Continuity Checker's 900 seconds is the longest interval of all because its job is inherently retrospective: contradictions accumulate across chapters, and checking after every single event would be paying the fleet's priciest analytical pass to re-read a story that has barely moved. Every one of these intervals is a settings knob (`author_interval`, `continuity_interval`, and so on — see [Scheduler and agent cadence](../reference/configuration.md#scheduler-and-agent-cadence-seconds) in the configuration reference), and an interval is a *floor*, not a schedule: it says "not more often than this," while readiness says whether there is any point running at all. How those two predicates combine — along with the dispatch pool, pass backoff, and watermarks the table has been gesturing at — is the subject of the next section.

## The scheduler: cadence, readiness, and concurrency

The scheduler (`Scheduler` in `novelizer/scheduler.py`) is deliberately small — about two hundred lines, no workflow graph, no queue broker, no state machine. It knows nothing about novels: agents are opaque objects with a name, a `paused` flag, an interval clock, and an async `readiness()` method that returns a float. Everything story-shaped lives on the agent side of that interface. What the scheduler owns is the answer to exactly one question, asked about once a second: *given who is allowed to run right now, and who most wants to, which agents get the free slots?*

That smallness is a design position, not an accident. Because the log is the only shared surface, the scheduler never has to route work, track dependencies, or deliver results — an agent's "input" is whatever the log contains when it runs, and its "output" goes through the committer. All the intelligence about *what* to do lives in the agents; all the control over *whether output lands* lives at the commit gate ([next section](#the-gated-commit-path)); what remains for the scheduler is pure dispatch policy, thin enough that its whole contract fits in three predicates: the interval says "not too often," the readiness score says "worth it right now," and the dispatch pool says "not too many at once."

### Tick loop and the dispatch pool

The loop itself is four lines: while running, call `tick()`, log (and survive) any exception, sleep one second, repeat. A crash inside a tick never stops the room — `run()` catches, logs, and keeps ticking.

Each `tick()` fills free slots in a *dispatch pool* of at most `max_concurrent_agents` simultaneous agent runs (default 2 — a live-applied settings knob; see [Scheduler and agent cadence](../reference/configuration.md#scheduler-and-agent-cadence-seconds) in the configuration reference). The tick first builds the eligible set: agents that are not paused, not already in flight, and whose interval has elapsed. It then scores that set by calling each agent's `readiness()`, sorts descending, and dispatches from the top until the slots are full — skipping anyone whose score is exactly zero, because a zero score means "running me would be a waste of an LLM call," and an empty slot is cheaper than a pointless run. Python's stable sort makes the registry order the tie-break, which is the only scheduling significance that order has (see the previous section).

The crucial property of `tick()` is that it does not wait. Dispatching an agent means creating an `asyncio.Task` and moving on; the tick returns as soon as tasks exist. As the method's own docstring puts it, "the tick cadence becomes the dispatch cadence, not a wait-for-completion cadence." An Author run that spends four minutes drafting a chapter does not freeze the room — it occupies one pool slot, and every subsequent tick keeps filling the other slot with whoever is ready. The in-flight map (keyed by agent name) is also what prevents the same agent from being dispatched twice concurrently: an agent mid-run is simply not eligible.

Why a pool of two rather than ten? Concurrency here is real overlap — two agents' LLM calls genuinely run at the same time — and the event store's write lock means their commits interleave safely. But every agent in flight is acting on the log as it stood at dispatch time, so the pool size is really a bound on *how stale a view you tolerate*: with two slots, at most one other agent's work can land while yours is in progress. Two gives enough overlap to hide LLM latency (the critics can judge while the Author drafts) without letting half the fleet act on the same snapshot and pile up redundant or conflicting intents for the commit gate to sort out.

When a run finishes — successfully or not — a `finally` block does the bookkeeping: the agent's interval clock is stamped, the in-flight slot frees, a per-agent run counter increments, and a "last completed" marker updates (a sticky display aid for the TUI, distinct from the honest in-flight flag, because fast agents finish between status polls). Failures are contained exactly as the [room-vs-pipeline section](#why-a-room-instead-of-a-pipeline) promised: the error string is recorded per agent for the status display, the exception is retrieved so asyncio does not complain about unawaited task failures, and — critically — the interval is consumed *even on a crash*. The comment in `_run` states the reason plainly: a crashing agent must back off "instead of staying eligible and hot-looping, which starves every other agent of scheduler slots." A broken agent degrades into an agent that fails once per interval; the other nine never notice.

The scheduler also narrates itself to the telemetry log (the separate `telemetry.db` event store described [earlier](#the-event-log-is-the-only-shared-surface)): a `scheduler.picked` event per dispatch, and a `scheduler.eligibility_changed` event per agent per state *change* — ready, paused, running, interval-not-elapsed, or readiness-zero — deliberately edge-triggered rather than a per-tick heartbeat, so the trace stays quiet enough to read. That trace is how you answer "why isn't the Editor running?" after the fact without ever having watched the room live.

### Intervals, pass backoff, and watermarks

An idle-but-polling agent is not free: readiness checks are cheap, but a dispatched run costs an LLM call even when the agent concludes there is nothing to do. The room therefore stacks three throttles in front of every dispatch, each engaging on strictly more knowledge than the last.

The first is the **interval** — a per-agent floor on dispatch frequency (`ready_for_interval` in `novelizer/agents/base.py`: at least `interval` seconds since the last run, and not inside a backoff window). It costs nothing to evaluate and knows nothing about the story; it exists so that even a permanently-eager agent cannot monopolize the pool. One subtlety: the timestamp stamped by `mark_ran` is the *dispatch* tick's clock, but it is recorded only when the run completes — so the interval measures dispatch-to-dispatch spacing, while the in-flight check covers the gap in between. Intervals are the settings knobs from the fleet table (`author_interval`, `muse_interval`, and the rest), and changes apply live to the running agents.

The second is **pass backoff**, which engages after a run that *did* happen but found nothing worth doing. An agent whose LLM pass explicitly returns a no-action verdict calls `note_pass()`, which pushes its next eligibility out to three intervals instead of one (`PASS_BACKOFF_MULTIPLIER = 3`). The reasoning: one empty pass is weak evidence, but it is evidence, and the polite response to "I looked and there was nothing" is to look less often for a while — freeing dispatch slots for agents with actual work. The backoff is per-verdict, not a decaying state: the next real run resets the rhythm.

The same backoff machinery also absorbs **endpoint saturation**. Every agent in the fleet (plus chat, embeddings, and the tool-call summarizer) shares one LLM server, so under load the server answers with 429s. Resilience is layered cheapest-first: each request retries with exponential backoff up to `LLM_MAX_RETRIES` (10) times — roughly a minute of patience, spent *inside* the run where waiting preserves the pass's in-flight tool work — and only if the limit outlasts that does the run die, at which point `run_once` recognizes the rate-limit error (even wrapped in a framework re-raise) and calls `note_rate_limited()`, stepping the agent back `RATE_LIMIT_BACKOFF_MULTIPLIER` (3) intervals. One agent waiting briefly is cheaper than one agent restarting a pass; one agent restarting is cheaper than ten agents hammering a limit that just proved itself exhausted.

The third and sharpest is the **watermark**, which prevents the empty run from happening at all. An agent that opts in implements `_fingerprint()` — a small tuple summarizing the external story state its work depends on (the World Architect's, for instance, is just the chapter count and the last chapter's id). `_gate_on_watermark` then forces readiness to zero whenever the current fingerprint matches the one recorded after the agent's last run: "nothing I care about has changed, so my score is not merely low, it is zero." This is where the log's total order quietly does work — "has anything changed?" is a trustworthy question only because state derives from a strictly growing sequence. Two details keep watermarks honest. Fingerprints deliberately cover only state the agent does *not* write (the Architect fingerprints chapters, never its own world entries), both so an agent's own commits cannot re-trigger it and because the read-store projection lags an agent's own just-committed writes by design. And the fingerprint is captured *before* the run and compared again *after*: if the story moved mid-run — entirely possible with two agents in flight — the watermark is left clear rather than recorded, so the next tick re-dispatches instead of wrongly absorbing work the run never saw. Escape hatches trump watermarks where they must: a pending director seed forces the Architect's readiness to 1.0 unconditionally, because a seed is external input the fingerprint does not track, and gating on it could starve a direct human instruction indefinitely.

The three layers compose into a cheap-to-expensive cascade: the interval gates on the clock (free), the watermark gates on a couple of projection reads (cheap), and pass backoff gates on the verdict of a full LLM pass (expensive — which is exactly why its finding is honored for three intervals). A quiet room settles toward near-zero LLM spend without any global "idle mode": each agent individually concludes there is nothing to do, at the cheapest layer able to reach that conclusion.

### Readiness scores, director overrides, and pausing

Readiness is the room's priority system, and its defining property is that the scheduler does not compute it — each agent self-reports, and the scheduler treats the float as opaque. The scores only have to be *comparable*, not calibrated: the fleet table in the previous section shows they are all shaped onto roughly the same 0-to-1 scale, with 1.0 meaning "urgent," small meaning "routine," and 0.0 carrying the one value the scheduler actually interprets — never dispatch. This is the same decentralization as the rest of the room applied to scheduling itself: just as no component knows what the Editor *does*, no component knows when the Editor *matters* — the Editor does, by reading the log. Adding an eleventh agent adds a readiness function, not a priority-table edit.

Two human controls cut across the scores, and they are deliberately asymmetric — one forces work in, one forces work out.

The **director override** forces an agent to the head of the line. A director signal of kind `override` naming a target agent (a `director_signal.created` event — like all steering, it goes through the log) is checked by every tick: if the target is otherwise eligible, it takes the first free slot *before* readiness scoring happens, bypassing the ranking and even a zero score — watermark and all. What the override does not bypass is telling: a paused target stays paused, an in-flight target stays single-instance, and an unelapsed interval still gates. The override is "you go next," not "break the safety rules" — it outranks the agents' own sense of priority but not the room's structural invariants.

**Pausing** removes an agent from consideration entirely. `pause` flips a flag the eligibility filter checks; the agent stops being dispatched but an in-flight run is never cancelled — it completes, commits (or is gated), and only then goes quiet, so pausing can never tear a half-finished run out of the room. Per-agent pause and resume are exposed as `:pause <agent>` / `:resume <agent>` in the TUI's command bar, and the global toggle (the `P` key) uses a carefully scoped pair: `pause_all` returns only the names it *newly* paused, and the resume side resumes exactly that list — so pausing the whole room and resuming it never clobbers an agent you had individually paused beforehand. The scheduler's `status()` snapshot (paused, genuinely running, seconds until next eligible, last error, run count, last completed) is what the TUI's roster renders; the run counter exists so the display can distinguish "still the same stale error" from "ran again, failed again" when the error text is identical.

It is worth closing on what the scheduler *cannot* do, because the boundary is the design. Nothing in this section decides whether an agent's output becomes canon: a dispatched agent runs at full capability regardless of autonomy level, and an overridden agent's chapter can still land as a proposal awaiting your approval rather than as an event in the log. Scheduling controls *when work is attempted*; the commit gate controls *what work counts* — and keeping those two levers independent is what lets you run a fully autonomous room slowly, a heavily gated room fast, or any combination in between. The gate is the next section.

## The gated commit path

The [event-log section](#the-event-log-is-the-only-shared-surface) ended on a deliberate gap: `EventStore.append` records anything it is handed, with no opinion about whether it *should*. The room's entire answer to "how does a human stay in control of ten autonomous agents?" lives in the layer between the agents and that append call — and the design bet is that control belongs at exactly one place. Agents do not write canon; they *declare* what they want written, every declaration funnels through a single committer seam, and that seam consults a policy that either appends the event or parks it as a proposal for a human to decide. Because there is one gate rather than ten agents' worth of scattered write sites, "how much do I trust the room right now?" is a dial you turn, not code you change — and turning it never requires touching, restarting, or even notifying a single agent.

### Declared intents, not direct writes

No agent can write to the `EventStore`. What every agent holds is a committer, and the only write operation in an agent's world is `committer.commit(agent_name, event_type, aggregate_id, payload)` — the agent names itself, names the event it wants, and hands over a typed payload. (One agent, the Continuity Checker, does hold a *read* handle on the store — its prose-mining pass scans the raw log for the unprojected `chapter.mined` markers described [earlier](#the-event-log-is-the-only-shared-surface) — but every call it makes is an `events_since` read; nothing in the agents package appends to the log except through a committer.) And most agents do not even call `commit` directly for their domain effects. Their LLM passes return structured output schemas whose fields are lists of *intents* — `ThreadIntent`, `KnowledgeIntent`, `CausalIntent`, `ThemeIntent`, `PromiseIntent`, `ArcIntent`, `BriefIntent`, `BeatIntent` and kin (`novelizer/agents/schemas.py`) — small declarative records like "touch thread X, here is my evidence" or "character Y learns secret Z." A shared library of commit helpers (`novelizer/agents/intents.py`) translates each intent family into the corresponding `thread.*` / `secret.*` / `promise.*` / `arc.*` events, and it is deliberately the only road by which those claims-about-canon reach a commit call — no agent hand-rolls a `thread.touched` from model output. The prose itself is the one exception that proves the rule: `chapter.created` and `chapter.revised` go through `commit` directly, because a chapter is the agent's own artifact, not a claim about existing canon ids that needs cross-checking.

That helper layer is the room's trust boundary against its own model output, and its rules are strict precisely because the projector's rules ([earlier](#the-event-log-is-the-only-shared-surface)) are lenient. The projector tolerates junk after the fact — unknown ids no-op, terminal states absorb — but the intent helpers try to stop junk from becoming a logged fact at all: an intent citing a thread, secret, character, or chapter id that is not in the caller's known-active set is dropped with a logged warning and no event (cited ids are lower-cased before the check, because canon ids are minted lowercase everywhere and a casing mismatch is an LLM transcription slip to absorb, not a new entity); a `plant` that collides with an already-live thread id is downgraded to a `touch` (the agent clearly meant "this thread is live," and a duplicate `thread.planted` would only be a projection no-op anyway); an invalid promise window is zeroed rather than committed, because "an invalid window must never enter canon"; and each caller passes an `allowed_actions` set that enforces role boundaries mechanically — the Character Keeper may commit `learn` knowledge intents but never `reveal`, because revealing a secret is a narrative-authoring act reserved for the Author and Editor. One rule runs the other way and says something about the philosophy: an intent that cites canon without quoting any supporting evidence is *warned about but still committed* — "an under-cited but real narrative beat is worth more than the silence of discarding it, and the warning rate is the measurement that would justify a stricter policy later."

Two things ride along with every commit because of this shape. The `agent_name` parameter exists so the gate can be per-agent — the committer signature was designed for gating before gating existed. And the run id from the ambient run context (`novelizer/run_context.py`, a `ContextVar`) is stamped onto every appended event, which is what makes the telemetry join from [the log section](#the-event-log-is-the-only-shared-surface) work: every event in canon knows which agent run produced it.

### The Committer seam and GatingCommitter

The seam itself is forty-six lines (`novelizer/canon/committer.py`), and its two classes are the design's before-and-after photographs. `Committer` — docstring: "The single seam through which agents write canon" — is the original full-auto implementation: `commit` appends the event, unconditionally. `GatingCommitter` is, per its own docstring, a "drop-in replacement for Committer that consults an AutonomyPolicy… Same public `commit` signature as Committer, so Runtime can swap the implementation with zero agent-code changes." Its `commit` asks the policy one question — `is_gated(agent_name, event_type)`? If no, it appends the event exactly as `Committer` would. If yes, it wraps the would-be event in a `Proposal` record (proposing agent, target event type, target aggregate id, the payload serialized to a plain dict) and appends a `proposal.created` event *instead*. The target event does not enter the log; a fact *about the desire for it* does. The `Runtime` always wires `GatingCommitter` (`novelizer/runtime.py`), so gating is permanently in the path — full autonomy is not a different committer but the policy answering "no" to almost every question, with one exception even `full_auto` cannot waive (`blueprint.adopted`, [next section](#autonomy-levels-and-gating-tiers)).

Three consequences of this tiny class are worth spelling out. First, **agents cannot tell they were gated.** `commit` returns nothing in either branch; an Author whose chapter became a proposal ran exactly the code path of an Author whose chapter became canon. There is no approval-waiting state in any agent, no callback, no retry logic — the agent's next run simply reads the log, and a gated chapter is indistinguishable from a chapter it has not written yet. All the machinery of supervision lives on one side of the seam. Second, **the gate cannot recurse**: `proposal.created` is appended directly by the committer rather than routed back through `commit`, so no autonomy level can gate the act of proposing itself. Third, **the gate governs agents, not you.** Director actions — seeds, focus signals, autonomy changes, approvals — append straight to the `EventStore` via the command layer (`novelizer/director/commands.py`), never through a committer. The human is not a participant the policy could gate; the human is who the policy reports to.

### Autonomy levels and gating tiers

The policy side (`novelizer/canon/policy.py`) is a classification of the event vocabulary crossed with a four-position dial. The dial is `AutonomyLevel` (`novelizer/canon/autonomy.py`): `full_auto`, `gated_retcons`, `gated_canon`, `gated_all` — a strict ladder in which each level gates everything the previous one did, plus one more ring of event types. The classification puts every event type in one of four buckets:

- **Always gated**, at every level: exactly one event type, `blueprint.adopted`. The payload's own docstring records why: "adopting a shape re-frames the whole book; the Director signs off." A room that can silently swap its story structure is a room you cannot leave alone at *any* trust setting. (The one sanctioned exception proves the rule from the previous section — a Director-authored adoption during story creation appends directly, because it happens before any `GatingCommitter` exists and "the creation form IS the sign-off"; agent-proposed adoption is always-gated, full stop.)
- **Retcon tier** (gated from `gated_retcons` up): `world_entry.superseded` and `flag.resolved` — the two events by which the Retconner rewrites what established canon *means*. Edits to the past are the first thing a cautious Director wants eyes on, before new prose is.
- **Canon tier** (gated from `gated_canon` up): the retcon events plus the facts of the story itself — world entries, character creation and updates, chapter creation, revision and status changes, secret reveals.
- **Never gated**, at any level: the long list of mechanical and steering events — chapter briefs, thread/promise/arc/theme bookkeeping, beat fulfillment, director signals and their consumption, agent remarks, chat, flag escalation, and every event the deterministic no-LLM Muse emits. These are gated-never not because they are safe but because gating them would break the room: a proposal queue full of `thread.touched` bookkeeping would bury the decisions that matter, and gating `director_signal.consumed` would mean the room needs permission to obey you.
- Everything else falls to a catch-all tier gated only at `gated_all` — the "trust nothing" setting where even newly filed flags queue for approval.

The tier *mechanics* are not Novelizer's: the `EventTypeRegistry`, `GatingTier`, and the `is_gated` ladder comparison live in `substrate`, the domain-neutral kernel, while `policy.py` supplies the fiction-specific buckets and the mapping from `AutonomyLevel` to a tier index — the same generic/specific split described in [Architecture boundaries](architecture-boundaries.md).

The dial itself is state *in the log*, like everything else: an `AutonomyState` carries a global level plus a per-agent override map (`level_for` answers overrides first, global otherwise), and changing it appends an `autonomy.changed` event projected into a singleton row. Two properties follow. Your trust decisions are part of the story's replayable history — a rebuilt projection knows exactly when you tightened the gate and for whom. And because `AutonomyPolicy.is_gated` reads the live state from the projection *on every commit*, a change takes effect at the very next commit — including commits from runs already in flight when you turned the dial. Per-agent overrides are what make the dial expressive: a room at `full_auto` with the Retconner overridden to `gated_retcons` is "run free, but I sign every rewrite of the past"; a room at `gated_canon` with the Author at `full_auto` is "draft freely, but I approve everything that reshapes the world around the prose." The operational commands are `novelizer autonomy LEVEL [AGENT]` from the shell and `:autonomy` in the TUI's command bar — see [`novelizer autonomy`](../reference/novelizer-cli.md#novelizer-autonomy-level-agent) in the CLI reference for exact syntax and the level table.

### Proposals and the human approval loop

A gated commit becomes a `Proposal` (`novelizer/canon/autonomy.py`): id, timestamp, proposing agent, target event type and aggregate, the exact payload, and a status that starts `open`. The projector folds `proposal.created` into a `proposals` table, and the open queue — an exact `status="open"` filter over that table — surfaces in two places. In the TUI, a high-contrast banner ("▼ 2 proposals awaiting approval — press a") polls the open count twice a second and appears only when the queue is non-empty; the `a` key then opens a modal approval screen (it refuses to open over an empty queue) that renders each proposal as *agent → target event* with a one-line payload summary, and the full payload as context for the highlighted row — enter approves, `x` rejects, escape closes. The screen is deliberately a thin shell: its decisions go through the same command dispatcher as a typed `:approve <id>`, never calling `ProposalService` directly, so a queue decision lands in the feed exactly like any other command. From the shell, `novelizer proposals` lists the same queue for scripting or a glance — see [`novelizer proposals`](../reference/novelizer-cli.md#novelizer-proposals).

Deciding is `ProposalService` (`novelizer/canon/proposal_service.py`), whose docstring is the whole contract: approve and reject are "the only two ways a proposal leaves the 'open' state." **Approve** appends two events — first the proposal's target event, with byte-for-byte the payload the agent proposed (via `append_raw`, since the payload was stored as a plain dict), then a `proposal.approved` marking the decision. From that moment the approved event is canon like any other: the projector cannot tell an approved chapter from a directly-committed one, and every agent sees it on their next read. There is deliberately no partial approval and no payload editing — the gate is a yes/no on the agent's work as proposed, because a payload you silently rewrote is a payload no log entry says anyone authored. If the work is almost right, the honest moves are to reject and steer (a seed, a chat note) or to approve and let the Editor's normal revision loop handle it. **Reject** appends one event, `proposal.rejected`; the target event is never appended, and the open-status guard makes the decision final — a later approve of a rejected proposal is a no-op, so a discarded action can never materialize afterwards. Notably, nothing notifies the proposing agent of either outcome: the decision events' only consumer is the projector, which flips the proposal's status row so it drops out of the open queue — no agent reads `proposal.approved` or `proposal.rejected`, and the agent, which never knew it was gated, simply proceeds from whatever the log now says. The commands are `novelizer approve` / `novelizer reject` (full proposal id required) and `:approve` / `:reject` in the TUI — see [`novelizer approve`](../reference/novelizer-cli.md#novelizer-approve-proposal_id) and [`novelizer reject`](../reference/novelizer-cli.md#novelizer-reject-proposal_id) for output and edge cases.

The loop's defining property is that it is **asynchronous and non-blocking**. A pending proposal stops nothing: the scheduler keeps ticking, ungated events keep committing, and the proposing agent keeps taking turns. The room does not wait for you — it routes around you, and the gated work waits in the queue, not the agents. That is the same shape as every other human control in this document, and it completes the set: pause and override (scheduler) govern *when agents act*; the autonomy dial governs *which of their actions need you*; approve and reject are *your verbs at the gate*. All four are log events or flags you can flip live, which is what lets the same room be a fully autonomous novelist overnight and a closely supervised drafting assistant the next morning, without a line of agent code knowing the difference.

## Coordination without messages

Every multi-agent system has to answer one question: when agent A's work matters to agent B, how does B find out? The mainstream answers are messages — a queue, a bus, an RPC call, a shared task object with a callback. Novelizer's answer is that B reads the log. There is no queue, no bus, no channel, and no agent-to-agent call anywhere in the system; the only story I/O an agent performs is reading the log (through its projections — or, in the Continuity Checker's one case, the raw event sequence) and committing through the committer seam. When one agent's work must reach another, it reaches it the way footprints reach a tracker: as durable marks on the shared surface, read on the reader's own schedule. This is the blackboard pattern the [opening](#the-room-in-one-paragraph) named — coordination through the state of the environment rather than through communication about it — and this section shows the actual mechanics, because "the agents coordinate through the log" is easy to say and easy to disbelieve until you watch a handoff happen.

Every handoff in the room is built from the same three moves. A producer appends events describing new state. A consumer's `readiness()` and `poll()` query the projection for state shaped like its job. And — the move that makes the whole thing work — *taking* the work is itself an event, so the queue, its contents, and its consumption all live in the same log as everything else. Four instances, spanning every kind of coordination the room does:

- **The draft queue** (Author ⇄ Editor). The Author commits `chapter.created`; the new chapter's editorial status is `draft`. That single fact is the entire handoff: the Editor's readiness (`drafts / 3`) rises because its poll counts draft chapters, and its next run takes the oldest one. Approval commits a `chapter.status_changed` to `reviewed` — which simultaneously drains the queue, lowers the Editor's own readiness, and raises the Author's (`1.0 − drafts/3`). No one told the Editor a chapter was ready; the chapter's own status *is* the notification, the work item, and the acknowledgment.
- **The brief runway** (Plotter → Author, and back). The Plotter commits `chapter_brief.drafted` events targeting future chapter ordinals. The Author's poll asks the projection one precise question — `get_open_brief_for_ordinal(len(chapters) + 1)` — and if a brief comes back, it is the chapter's assignment. On committing the chapter, the Author also commits `chapter_brief.fulfilled`, which shortens the Plotter's runway of open briefs ahead of the chapter count and raises its readiness to plan the next one. The Plotter even cleans the shared surface the same way: a mechanical pre-pass supersedes any open brief whose target ordinal the book has already passed (`chapter_brief.superseded`) — housekeeping is also just events.
- **The Muse's hand** (Muse → Author). The Muse deals `inspiration.drawn` and its readiness drops to exactly 0.0 while an unconsumed hand sits on the table. The Author, when it drafts, commits `inspiration.hand_consumed` alongside the chapter — and the Muse's readiness flips back to 0.9, so the next cycle deals fresh. That is producer flow control with no channel and no counter: the hand's own lifecycle in the log is the protocol, and it keeps exactly one hand ahead of the Author forever.
- **The flag pipeline** (everyone → Triage → owners). Any agent that finds a problem outside its lane files `flag.created` — the Author for a brief that fights a voice card, the Editor for craft and voice-drift issues, the Continuity Checker for contradictions — deduplicated at filing against the open queue in that category, since a re-polling agent would otherwise refile the same finding every cycle. Triage polls *all* open flags and disposes of each: dismiss (`flag.rejected`), escalate a critical one (`flag.escalated`), reclassify a mislabeled one, or leave it open for its owning agent's poll to find — routing decided by a plain category-to-agent-name map (`_CATEGORY_OWNERS` in `novelizer/agents/triage.py`). The Retconner's poll picks up open `contradiction` flags and closes each with `flag.resolved` or `flag.rejected`. Three agents, a full issue-tracking workflow, and not one of them has ever addressed another.

The closest thing to a message the room contains is worth examining precisely because it tests the claim. When the Editor's verdict is *revise*, it commits a `director_signal.created` with `kind=revise`, `target_agent="author"`, the chapter id as target, and the rewrite instructions as body (`novelizer/agents/editor.py`). That is addressed, directed, and instructional — surely a message? Look at what it is not. It is not *delivered*: the Author finds it because its own poll asks for unconsumed signals targeting it, on its own next eligible run. It is not *private*: it is an event in the log, visible in the feed, to the Director, and to a replay. It is not *transient*: a crash or restart anywhere between verdict and rewrite loses nothing, because the handoff was durable the instant it was committed. And it is not *awaited*: the Editor's run ends with no callback and no future; the eventual `chapter.revised` cites the signal's id as `editor_notes_ref`, flips the chapter's status back to `draft` — landing it back in the Editor's queue by the same status mechanics as before — and the Author marks the signal `director_signal.consumed`. Even the potential infinite loop this creates is broken by the log rather than by negotiation: the projection increments `revision_count` on every revision, and the Editor force-approves any chapter that has spent its budget (`MAX_REVISIONS = 2`), as a system invariant rather than a prompt suggestion. Note, finally, whose vocabulary the Editor is speaking: `revise` is a `SignalKind` alongside the Director's own `seed`, `focus`, `note`, and `override`. The one agent that needs to direct another does it through the human's steering channel, in public, in a form the human could have used — not through a private agent-to-agent protocol.

It would be slightly too clean to say no agent knows another exists. A few names do appear in the data: the Editor writes `target_agent="author"`, and Triage's owners map names `retconner`, `plotter`, `structure_analyst`, `world_architect`. But these are addresses in payloads, not dependencies in code — no agent imports, constructs, holds, or calls another, and the difference shows up under failure. Pause the Retconner for a week and contradiction flags simply stay open in the projection, visible in the TUI, ready for its return (or for a replacement agent that polls the same category); nothing times out, nothing bounces, no sender is holding a broken reference. In a message system, an absent recipient is a delivery failure someone must handle. Here, an absent recipient is just a queue that isn't draining — a fact you can see, not an error anyone has to catch.

What the room buys with this discipline: **durability** — a handoff cannot be lost in flight, because there is no flight; the room restarted mid-story resumes every pending handoff from the log exactly where it stood. **Observability** — every act of coordination is an event in the feed, so watching the room *is* watching the coordination; nothing happens in a DM. The design is pointed about this: even your chat with an agent is `chat.user_messaged` / `chat.agent_replied` events, while the agents' one purely social output, `agent.remarked`, is deliberately never projected — agents cannot read each other's remarks, so the feed's banter is for you and can never become a covert side channel. **Openness** — the [fleet section](#the-ten-agent-fleet-and-its-scheduling-order) claimed an eleventh agent needs only a registry entry, and this is why: "coordinating with all ten existing agents" and "reading and writing the log" are the same activity, so integration is not a step. And what it costs: **latency** — coordination advances at poll cadence, not delivery speed, so a revise verdict can sit until the Author's next eligible run; acceptable when the work unit is a chapter, and exactly the property you would not accept in a system where handoffs are measured in milliseconds. **No acknowledgment** — a producer cannot know its work was picked up, only observe, later, that a consumption marker (`fulfilled`, `consumed`, `resolved`) appeared; the readiness see-saws are what keep unconsumed work self-limiting in the meantime. **Stale reads** — two in-flight agents each act on the log as it stood at dispatch, which is why the [projector's idempotency rules](#the-event-log-is-the-only-shared-surface) and the filing-time dedup exist at all. The [next section](#alternatives-considered) weighs this trade against the architectures that make the opposite one.

## Alternatives considered

Every section so far has gestured at a road not taken; this one walks each of them far enough to see why the room turned back. Two of these alternatives are not hypothetical — the repository's design specs record them as shapes the system actually had and deliberately replaced — and the rest are the mainstream architectures a multi-agent system is expected to be. Each is judged with the full picture now in hand: the log, the fleet, the scheduler, the gate, and the message-free coordination those four make possible.

**The pipeline, revisited.** The [second section](#why-a-room-instead-of-a-pipeline) rejected the pipeline on narrative grounds — revision is permanent, not a stage — but the later sections sharpen the case into a structural one. Look at the loops this document has since described: draft → review → revise → review again, budget-capped at `MAX_REVISIONS = 2`; canon → contradiction flag → triage → retcon → re-check; propose → human decision → the room already three turns further along by the time you decide. Every one of them is a cycle, and a pipeline is by definition acyclic — modeling the room as a pipeline means either forbidding the cycles (no revision, no retcons, no asynchronous human) or encrusting the DAG with back-edges until it is a state machine nobody drew on purpose. The pipeline's one genuine virtue, guaranteed ordering, is exactly what the room chose to spend: it buys continuous steering (pause, override, and the autonomy dial work at any instant because there is no phase to interrupt) and local failure (a crashed agent backs off alone instead of stalling a stage). The room does not lack the pipeline's discipline — it relocates it, from a fixed execution order into the commit gate and the projector's invariants, where it constrains *what becomes true* rather than *when work may happen*.

**A workflow-graph engine between the agents.** This one is sharpened by the fact that a workflow-graph engine is literally in the building. Every tooled agent's LLM pass is built with `create_deep_agent` from LangChain's deepagents library, which runs on LangGraph — planning, a scratch filesystem, canon-read tools, even a delegated `researcher` subagent an agent can dispatch mid-pass (`novelizer/agents/subagents.py`); the recursion-limit comment in `novelizer/agents/base.py` notes that tool-heavy passes "can exceed LangGraph's default of 25" steps. So the room's designers did not reject graph orchestration — they scoped it. A graph engine governs work that has a beginning, an end, and a knowable shape: one agent's pass, minutes long, ending in a structured verdict. It is never used to wire agents *to each other*, because the book-length process has none of those properties — no end state, no fixed shape, and a human who may redirect it at any tick. The vision spec draws the line in one sentence: "LangGraph checkpointing persists agent execution state only. Agents never message each other; the event log remains the only coordination channel" — and, a few lines earlier, "LangGraph checkpointing state is *agent plumbing*, never canon" ([2026-07-17 vision design](../superpowers/specs/2026-07-17-novelizer-vision-design.md)). The boundary has already paid for itself once: the same spec records the intra-agent engine being swapped wholesale — "rebuilt on LangChain's deepagents library over LangGraph, replacing pydantic-graph entirely" — with the room's coordination surface untouched, because the coordination surface never knew what ran inside a pass.

**A shared mutable store.** This is the alternative the system actually shipped with and tore out. The [event-sourced store design spec](../superpowers/specs/2026-06-19-event-sourced-store-design.md) opens with the verdict: "Replace the current shared-state polling store with an event-sourced architecture." The original design had agents polling and mutating a shared `Store` facade of current-state rows — the obvious database shape, and the wrong one for this system, for a reason the fleet makes vivid: in this room, *history is a workload*. The Continuity Checker and Retconner exist to interrogate what was previously established; the Editor's revision budget counts how many times a chapter has been rewritten; the Structure Analyst scores a trajectory. A mutable store destroys the very thing those agents inspect — an `UPDATE` that "fixes" a contradiction also erases the evidence that it existed, which is why the room's retcons are `world_entry.superseded` events that leave the original on the record. The mutable store also has nothing to say about two writers: with the dispatch pool overlapping agent runs, in-place mutation means last-write-wins races, while appends merely interleave under the store's write lock. And the machinery half this document leans on — watermark fingerprints, deterministic replay, rebuild-from-scratch projections, the `run_id` audit join — all falls out of one strictly growing sequence and exists in no natural form over a table of current values.

**An orchestrator agent.** The reflexive modern design: a manager LLM that reads the state of the work, decides who should act, and assigns tasks — agents as workers, intelligence at the top. The room inverts this completely. Its "orchestrator" is `Scheduler`: 215 lines of deterministic asyncio whose imports include `asyncio`, `logging`, and `time` but no model client, and which — as the [scheduler section](#the-scheduler-cadence-readiness-and-concurrency) showed — treats agents as opaque floats. The judgment an orchestrator centralizes ("who should act now?") is instead decentralized into ten small `readiness()` functions, each a few lines of arithmetic over projection queries. What the inversion buys: the priority logic is testable and inspectable arithmetic rather than a prompt; a wrong readiness score mis-schedules one agent, where a confused orchestrator mis-schedules the whole room; deciding costs projection reads, not an LLM call per cycle for the lifetime of the story; and the roster stays open, because an orchestrator must know every worker's capabilities while the scheduler knows nobody's. The general principle is the same one behind the intent helpers: the room spends LLM judgment on the work itself and keeps the *control plane* — scheduling, gating, projection — deterministic, because control-plane code is exactly where a hallucination is unaffordable and where a hundred lines of Python is genuinely sufficient.

**One agent instead of ten.** Modern models are capable enough that "a single agent with tools, drafting the whole book in a long loop" is a serious proposal, and it would delete most of this document. It was not taken, for reasons every section has touched: the fleet's generator/critic split exists because a critic that can rewrite what it criticizes drifts into doing the writing badly, and the only structural way to enforce "You are a JUDGE, not a writer" is for the judge and the writer to be different agents — one prompt cannot hold ten adversarial pressures in tension with itself. The economics need the split too: the Author can run a stronger model than the rest of the fleet (`author_model` vs `agent_model` in `novelizer/settings/models.py`), the Continuity Checker's expensive pass runs at a 900-second cadence while the Muse polls at 60 for free — a mega-agent pays its best model's price for its cheapest bookkeeping. And the entire control surface of [the gated commit path](#the-gated-commit-path) presupposes plurality: per-agent autonomy overrides, per-agent pausing, and a proposal queue attributing each payload to a named role are meaningless when there is only one actor. A single agent would also carry the book in its context window; the fleet carries it in the log, where it cannot be forgotten, compacted away, or silently mutated. The honest form of the alternative survives *inside* the room: an agent's pass may spawn subagents to fan out work it owns — but a subagent is scoped to one pass and reports back to its dispatcher, never to the log directly.

**A blocking gate.** Given that a human approval gate was wanted, the textbook shape is synchronous: the gated agent's commit blocks until the Director decides, or — cheaper still — gated agents simply are not scheduled until the human is present. Both were rejected, and the `GatingCommitter`'s shape is the record of the rejection. Blocking would smuggle waiting state into every agent — futures, timeouts, resumption logic — exactly the machinery whose absence makes agents simple; instead `commit` returns nothing in both branches, and the room routes around an absent human rather than stalling on one. Gating at dispatch would be worse: it prevents the *work*, not just the commit, so there would be nothing concrete to decide about — where the proposal captures the exact payload, letting the Director judge a finished chapter rather than authorize a hypothetical one, and keeping the scheduler's "when to attempt" fully independent of the policy's "what counts." One smaller road-not-taken is preserved in the specs: the vision design originally sketched gating as a per-type `*.proposed` event vocabulary (a `chapter.proposed`, a `world_entry.proposed`, and so on). The implementation replaced that with the single generic `proposal.created` envelope wrapping any target event — which is why the policy's catch-all tier works at all: a brand-new event type is gateable at `gated_all` the day it is minted, with no parallel `*.proposed` twin to define, and the approval path (`append_raw` of the stored payload) is one code path instead of one per type.

The pattern across all six is consistent. Where an alternative offered *coordination machinery* — stage graphs, message delivery, an orchestrating mind — the room declined it, because the log already coordinates and every additional channel is another place where state can live unobserved. Where an alternative offered *judgment in the control plane*, the room declined that too, keeping scheduling and gating deterministic and spending the model budget on prose and critique. The result is a system whose complexity is almost entirely in its data — one log, richly typed — and whose code paths are short enough that this document has been able to cite most of them by line. What that shape costs, and where its edges are, is the subject of the next section.

## Consequences and trade-offs

Every architecture is a purchase, and the previous sections have mostly shown what the room bought: handoffs that cannot be lost because there is no flight, a history that cannot be silently rewritten, a control surface (pause, override, the autonomy dial, the proposal queue) that works live because it is all flags and log events, failure contained to one agent's backoff, and a roster open to an eleventh member for the price of a registry entry. This section is the other side of the receipt — what the design costs, where its edges are, and which of those edges are accepted on purpose versus merely tolerated for now. None of these are hypothetical; each one is visible in the source as a mitigation, a hard-coded constant, or a comment admitting the debt.

**The log grows forever, and everything downstream pays rent on it.** Append-only means the store has no delete — and also no compaction, no snapshotting, no archival tier: `novelizer/canon/event_store.py` is 128 lines, and none of them shrink anything. Every superseded world entry, every rejected proposal, every rewritten draft's original prose is in the file for the life of the story, and a projection rebuild is a full replay from sequence zero. The room accepts this because its scale is a novel, not a firehose: the workload is thousands of events, not billions, and SQLite reads them faster than any agent thinks. But the acceptance is a bet on scale, not a solved problem — a room left running across many books, or an event vocabulary that grows chattier, eventually meets the replay bill. The design's answer, when that day comes, is already implied by its own doctrine: projections are disposable caches, so snapshotting is an optimization of the cache, never a rewrite of the truth.

**Everything the agents see is slightly stale, at three separate lags.** The log is the truth, but no agent reads the log — agents read projections, which the projector refreshes on a polling loop (`projector_interval`, default 0.5 seconds, in `novelizer/settings/models.py`; the worker loop is in `novelizer/tui/app.py`). That is lag one, and it is why an agent's own just-committed writes are invisible to its own next read — a fact the watermark design ([earlier](#intervals-pass-backoff-and-watermarks)) treats as a feature to design around rather than a bug to fix. Lag two is dispatch staleness: an in-flight agent acts on the log as it stood when its run began, so with two slots, one agent's whole run can land while another is mid-flight. Lag three is poll cadence: a revise verdict committed by the Editor waits until the Author's next eligible run — up to the 300-second `author_interval` floor — before anyone acts on it. The room's compensations are the ones this document has already toured (idempotent projection rules, filing-time dedup, a pool bounded at two, `MAX_REVISIONS` as a loop-breaker), and they work because the unit of work is a chapter: minutes of staleness against hours of drafting is noise. The trade would be unacceptable in a system whose handoffs are measured in milliseconds — which is precisely why this architecture suits a writers' room and not, say, a trading floor.

**The non-blocking gate converts waiting into a different kind of staleness.** Because the room routes around a pending proposal instead of stalling on it, the payload you eventually approve was authored against a log that has since moved on — approval appends the stored payload byte-for-byte, into a story that may be several chapters further along. The design absorbs this the same way it absorbs everything: an approved chapter lands in editorial status `draft` like any other, so the Editor's normal review pass is the safety net for approved-but-now-awkward work, and the projector's absorbing rules make a stale bookkeeping event a no-op rather than a corruption. The related cost is coarseness: the gate is yes/no on the exact payload, with no editing and no partial approval — deliberate, as [the proposals section](#proposals-and-the-human-approval-loop) argued, but it means fine-grained content steering must travel the long way around, through seeds, chat, and rejection. And at `gated_all` the arithmetic turns on you: the room keeps generating at machine speed while decisions drain at human speed, and nothing bounds the open queue. The strictest autonomy level is honest about what it is — a mode where your attention is the room's scarcest resource — and the per-agent overrides exist largely so you never have to pay that price fleet-wide.

**An idle room is nearly free; a busy room is a continuous bill.** Every dispatched run of every agent except the Muse is at least one LLM call, and the room's whole scheduling apparatus — interval floors, pass backoff, watermarks, zero-score skips — is best read as cost-control machinery stacked in front of that fact ([the throttle cascade](#intervals-pass-backoff-and-watermarks)). The knobs that shape the bill are all in settings: per-agent intervals, `max_concurrent_agents`, the `author_model`/`agent_model` split that reserves the expensive model for prose, and a hard `llm_max_tokens` cap (4096) on every runner because, as the comment in `novelizer/settings/models.py` notes, uncapped local models "can generate past a proxy's request timeout, so no request ever completes." But the throttles only bound *wasted* spend; useful work costs what it costs, and a room drafting at full autonomy pays for it around the clock. That is the point — the product is a novel written while you sleep — but it means the meaningful cost decision is not in any single knob; it is the autonomy dial and the pause key, which are as much budget controls as trust controls.

**Agents see slices of canon, not canon.** The log never forgets, but a prompt has a budget, and the pushed context each agent receives is built from truncated projections — the Author's world block is ten entries at 150 characters of body each (`novelizer/agents/author.py`), prior chapters arrive as 200-character summaries, and the Continuity Checker's fallback context cuts prose at 300 characters. These character-count cutoffs are the room's sharpest known edge: a fact that lives beyond the cutoff is a fact the agent's pass never saw, and the repository's history includes exactly that class of bug (a character introduced past a prose truncation, invisible to the agent responsible for discovering her). The structural mitigation is the pull-tool layer: tooled agents mount a read-only virtual filesystem over canon (`novelizer/canon_fs/`) with `ls`, `grep`, `glob`, and `read`, so a pass that needs the full text of anything can fetch it mid-run instead of trusting the pushed excerpt — the backend's own error message enforces the one-way door: "Canon is read-only. To change the story record, declare intents in your structured response." The honest status is that the room is mid-migration between the two postures: push-context slices remain the default diet, pull tools are the escape hatch gated per agent by settings flags, and the trade — bounded prompts versus guaranteed visibility — is settled per agent, not globally. The debt is on the record, not just in this paragraph: the [canon pull tools spec](../superpowers/specs/2026-07-19-canon-pull-tools-design.md) names the Author and Continuity Checker as the "worst truncation pain," and the [context-assembly protocol spec](../superpowers/specs/2026-07-22-context-assembly-protocol-design.md) designs the eventual replacement for character cutoffs, under the invariant it states as "never silently truncate."

**The pull tools truncate too, and now say so.** The escape hatch has its own cutoff: `read_file` is deepagents' tool, and when the model omits `limit` the middleware supplies `DEFAULT_READ_LIMIT = 100`. The slice used to come back bare — a hundred lines of a chapter, no marker, no line count — so an agent told to read the previous chapter IN FULL read half of one and believed it had complied; four of the five chapters in the first full novel run were longer than that default. Every canon backend now slices through `sliced_read` (`novelizer/canon_fs/reads.py`), which appends a system-labelled line naming the window, the file's true length, and the arguments for the follow-up call, and the shared retrieval note tells agents to pass `limit=2000` when they mean a whole file. The notice quotes no path on purpose: `CompositeBackend` strips the route prefix before delegating, so a routed backend never sees the path the agent typed.

**Emergence has no warranty.** The draft-queue see-saw, the flag pipeline, the Muse's one-hand-ahead flow control — none of these are enforced anywhere; they are equilibria that fall out of ten readiness functions reading the same tables. Nothing proves they converge, no fairness mechanism ages a starving agent's priority upward, and a mis-shaped readiness function fails silently: the agent simply never wins a slot, and the room's output degrades in whatever way that agent's absence implies. The design's answer is diagnosis rather than prevention — the readiness functions are a few lines of testable arithmetic each, and the telemetry trace (`scheduler.picked`, `scheduler.eligibility_changed`) exists precisely to answer "why isn't the Editor running?" after the fact. The same softness governs the end of the book: completion is assessed by pure functions over the blueprint's shape (`novelizer/brain/completion.py` — every beat fulfilled, every promise settled, every arc resolved; "the blueprint's shape is the criterion, not its length"), and when it is satisfied the Plotter mechanically declares `book.completed`. But no readiness function consults that fact, and nothing halts: the endgame is steered by prompt ("Write the ending — then the room is done," the completion faculty's note tells the Plotter) and finished by a human. A room that is done is a room you stop — quiescence is emergent and stopping is the Director's job, which is coherent with everything else in this document and still worth saying plainly: left alone forever, nothing guarantees the room ever stops writing.

**Replay reproduces the record, not the process.** The log's determinism claims are real but narrower than they sound: the same log always rebuilds the same projections, and the Muse's recorded seed re-derives the same hand. What is *not* reproducible is the room itself — every other event's payload is the recorded output of an LLM call, so re-running the fleet from the same starting point yields a different book. The log is a perfect history of the run that happened, not a program that regenerates it. This is the accepted meaning of "deterministic" here, and it shapes what the log is for: audit, rebuild, and forensics (`run_id` joins every canon event to the agent run and telemetry that produced it), never re-execution.

**One room, one file, one machine.** The store is SQLite, the write lock is in-process asyncio, and the concurrency story is hardened for exactly the contention that actually occurs — `novelizer/canon/db.py` sets WAL mode and a 10-second busy timeout and wraps writers in lock-retry backoff because, per its own comment, "world.db has multiple writer connections (EventStore, Projector, headless CLI processes)." That is the full extent of the room's distribution ambitions: several processes on one machine sharing one file. There is no server, no replication, no multi-writer story across machines — and for a single-tenant creative tool that is the right amount of infrastructure, but it is a ceiling, and the ceiling is load-bearing: the log's total order, which watermarks, projections, and the audit trail all stand on, is cheap precisely because one SQLite file on one disk hands it out for free.

The through-line is the same trade made over and over: the room consistently buys *simplicity of machinery and totality of record* and pays in *latency, spend, and guarantees*. Where a conventional system would add a mechanism — a message bus for latency, a snapshot store for replay cost, a fairness scheduler for starvation, a hard terminal state for completion — this one adds a fact to the log, a note to a prompt, or a knob to settings, and leaves the human holding the levers. Whether that is the right trade depends entirely on the workload, which is why the honest summary is conditional: for a system whose unit of work is a chapter, whose operator is one person, and whose worst failure mode is a bad paragraph rather than a lost payment, the costs land on the cheap side of every one of these ledgers. Change those conditions and the same design would be wrong — which is perhaps the most useful thing an explanation can say about it.
