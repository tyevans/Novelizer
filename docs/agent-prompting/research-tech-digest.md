# Agent-prompting research digest — for the 8 novelizer agent redesigns

Every item below is a design rule you can apply directly to an agent's system prompt or scaffold. Sources cited inline. Rules that touch the whole fleet are marked [FLEET].

## 1. deepagents / create_deep_agent internals — compose WITH the harness, don't fight it

- **Your `system_prompt` is INSERTED as "custom instructions" inside a much larger base prompt** that deepagents ships (a generalized clone of Claude Code's prompt). So write each agent prompt as a *role + task specialization*, NOT as a from-scratch complete prompt — the base already covers tool-use mechanics, planning, and filesystem conventions. Duplicating that guidance wastes your attention budget and can conflict. [FLEET] (blog.langchain.com/deep-agents; docs.langchain.com deepagents overview)
- **Three middlewares are auto-attached: PlanningMiddleware, FilesystemMiddleware, SubAgentMiddleware.** Each injects its own dynamic system-prompt section and tools. Assume `write_todos`, the 8 filesystem tools (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`, `execute`), and a `task` (subagent) tool already exist and are already described — reference them by name in your prompt rather than re-explaining them. (docs.langchain.com deepagents overview)
- **The planning tool (`write_todos`) is "basically a no-op" — a context-engineering device to keep the agent on track.** For a fiction agent this is the single cheapest lever: instruct the agent, at pass start, to write a short todo list of what it will check ("read latest chapter → grep for open threads → verify continuity of X"). The act of planning measurably improves multi-step execution even though the tool does nothing. (langchain.com/blog/deep-agents)
- **`read_file` returns line numbers and supports offset/limit; `grep` has multiple output modes; `glob` matches patterns.** This is a Claude-Code-style index-then-read surface — prompt agents to grep/glob to LOCATE, then `read_file` to pull only the needed span, rather than reading whole canon files. (docs.langchain.com deepagents overview)
- **FilesystemMiddleware supports a `tools` allowlist; any filesystem tool you omit is stripped from BOTH the tool list and the middleware's dynamic prompt section.** If an agent (e.g. a read-only Continuity Checker) should never write canon, omit `write_file`/`edit_file`/`delete` — this removes the temptation and the prompt bloat in one move. [FLEET] (docs.langchain.com deepagents overview)
- **Subagents give isolated context windows and return only their final result.** For agents whose job spawns a heavy sub-investigation (e.g. Retconner tracing a contradiction across many chapters), delegate to a subagent so the parent's context isn't flooded with raw reads. (github.com/langchain-ai/deepagents; docs overview)
- **Prompt caching is automatic on Anthropic/Bedrock models for the STATIC prompt sections** (base instructions, memory, skills). Design corollary: keep the per-agent system_prompt STABLE across passes and push the volatile per-pass context into the user message — this maximizes cache hits and cuts latency/cost on interval-driven agents. [FLEET] (WebSearch synthesis of deepagents docs; blog.langchain.com/deep-agents)
- Context management is built in (summarize long threads, offload large tool outputs to the virtual filesystem). Don't hand-roll your own summarization inside prompts; lean on the harness and instead prompt agents to write durable NOTES to canon files for cross-pass memory. (github.com/langchain-ai/deepagents)

## 2. Frontier-lab agent-prompting rules — "right altitude" and simplicity

- **Aim for the "Goldilocks altitude": specific enough to steer, general enough to leave heuristics.** Avoid both brittle if-else rule dumps AND vague high-level platitudes. For fiction agents: give concrete triggers ("flag when a character's stated eye color differs from an earlier chapter") but not an exhaustive taxonomy of every possible error. [FLEET] (Anthropic, Effective context engineering for AI agents)
- **Structure every system prompt into labeled sections** using Markdown headers or XML tags — e.g. `## Role`, `## What to look for`, `## Tools & how to use them`, `## Output`. Distinct sections parse better than prose walls. [FLEET] (Anthropic, Effective context engineering)
- **Minimalism ≠ shortness: find the smallest set of HIGH-SIGNAL tokens.** Every token spent depletes a finite "attention budget"; context rot is real. Cut redundant instructions, but keep the guidance that actually changes behavior. [FLEET] (Anthropic, Effective context engineering)
- **Teach behavior with a few diverse, canonical EXAMPLES, not exhaustive rule lists.** Few-shot examples of "here's a real thread worth emitting / here's a non-event to skip" outperform enumerating edge cases. This directly raises tool-parameter accuracy (72%→90% in Anthropic's tests). [FLEET] (Anthropic, Effective context engineering; Anthropic, Advanced tool use)
- **Prefer simplicity; add agentic complexity only when a simpler prompt demonstrably fails.** Don't stack conditional logic into a prompt preemptively. (Anthropic, Building effective agents)
- **Make planning/reasoning explicit ("transparency" pillar).** Prompt the agent to state its plan (via `write_todos`) before acting — planning surfaces improve reliability on open-ended, unpredictable-step tasks, which fiction analysis is. (Anthropic, Building effective agents)

## 3. Pull-based / agentic-retrieval — make agents actually USE their tools

- **Adopt Claude Code's hybrid model explicitly: a small stable "map" pushed up front + just-in-time pull via glob/grep/read.** Push only lightweight identifiers (canon file paths, a table of contents, character/thread index); let the agent pull the actual prose on demand. This defeats stale-summary writing without pre-loading everything. [FLEET] (Anthropic, Effective context engineering — "Claude Code employs a hybrid model")
- **Name the anti-pattern in the prompt: "Do NOT write from the push summary alone."** The push context is a *pointer*, not the source of truth. Require the agent to read the relevant canon before emitting any intent about it. This is the direct fix for under-retrieval / stale-summary drift. (Anthropic, Effective context engineering; corroborated by AgentAbstain findings on over-confident acting)
- **Prescribe an index-then-read loop as the standard motion:** `glob`/`grep` or `search_canon` to LOCATE candidates → `read_file` with offset/limit to pull only the needed span → act. Naming the loop raises tool usage and prevents both extremes. (Anthropic, Effective context engineering; docs.langchain.com deepagents)
- **Ground every emitted intent in a citation (file path + line/heading).** Requiring a source reference forces the read to actually happen and makes over-retrieval self-correcting (the agent stops once it has the citing span). Grounding is the practical stopping criterion. (Anthropic, writing-tools-for-agents; contextual-retrieval)
- **Give an explicit stopping rule to curb over-retrieval / turn-burning:** e.g. "Once you can cite the evidence for your finding, stop searching and emit." Retrieval interplays with the recursion/turn limit — an agent with no stop rule will spend its whole turn budget browsing. (Anthropic, Effective context engineering; writing-tools-for-agents)
- **Metadata is signal: tell agents to exploit folder hierarchy, filenames, and timestamps** to decide what's current vs stale (e.g. latest chapter file, most recent revision). (Anthropic, Effective context engineering)

## 4. Tool responses & tool descriptions — the ACI matters as much as the prompt

- **Use natural-language / 0-indexed identifiers, never raw UUIDs, in anything the agent reads or emits.** Semantically meaningful names measurably improve Claude's retrieval precision and cut hallucination. For novelizer: reference characters/threads/chapters by human names/slugs, not opaque IDs. [FLEET] (Anthropic, writing-tools-for-agents)
- **Return high-signal fields only; strip low-level cruft** (mime types, pixel URLs, internal hashes) from `search_canon`/tool outputs. Give agents `name`-style fields, not technical plumbing. (Anthropic, writing-tools-for-agents)
- **Tool descriptions deserve the same prompt-engineering effort as the system prompt** — write them like docstrings for a new hire, with usage examples and clear boundaries between similar tools ("use `search_canon` for semantic/thematic lookup; use `grep` for exact strings/names"). If a human can't say which tool applies, the agent can't either. [FLEET] (Anthropic, writing-tools-for-agents)
- **Add usage EXAMPLES to tool defs, not just JSON Schema.** Schema says what's structurally valid but can't express when to include optional params or which combinations make sense — examples lifted parameter accuracy 72%→90%. Give each intent-emitting tool a filled-in example. (Anthropic, advanced-tool-use)
- **Make tool responses token-efficient: default pagination/truncation/filtering, with a steering note in truncated output** ("results truncated — narrow your query"). Prevents a single `search_canon` from eating the context window. (Anthropic, writing-tools-for-agents)
- **Errors must be actionable, not tracebacks** — a good error message ("no file matched; try glob 'chapters/*.md'") teaches the agent to recover instead of stalling. (Anthropic, writing-tools-for-agents)
- **Consolidate toward workflow-shaped tools over thin API wrappers**, and namespace related tools with consistent prefixes (`canon_search`, `canon_read`) so selection is easier. (Anthropic, writing-tools-for-agents)

## 5. Structured output + tool use — the highest-risk interaction for this system

- **Known failure mode confirmed: enforcing a response schema SUPPRESSES tool-calling and degrades reasoning ("constraint tax").** With `response_format=pydantic`, the model is biased to emit the final structure EARLY and skip the tool loop. Treat this as the #1 threat to pull-tool usage in novelizer. [FLEET] (arXiv 2606.25605, "Constraint Tax… Tool Calling Suppression Under Structured Output Constraints"; corroborated by structured-output guides, e.g. agenta.ai, pockit.tools)
- **Separate the two phases in the prompt: RESEARCH first (tools), THEN emit structure.** State explicitly: "First use tools to gather and cite evidence. Only after you have read the canon should you produce the final structured output." Naming the phase order counteracts the schema's pull toward premature finalization. [FLEET] (mitigation of constraint tax; Anthropic Building effective agents "transparency/planning")
- **Require evidence/citation FIELDS inside the output schema** (e.g. `evidence: list[str]` of file:line citations per intent). A schema that demands grounding cannot be satisfied without first calling tools — this structurally forces the tool loop the constraint tax would otherwise skip. [FLEET] (synthesis: writing-tools-for-agents grounding + constraint-tax mitigation)
- **Guard the opposite failure too — emitting structure AFTER a long tool loop.** Add a checkpoint: "When you have your evidence, STOP researching and emit the structured result now." Long tool loops can drift and never finalize. (Anthropic, Effective context engineering — stopping criteria; deepagents context-mgmt)
- **Keep the structured schema lean.** The heavier/more constrained the schema, the higher the constraint tax on reasoning — minimize required fields and avoid deeply nested structures where a flat one works. [FLEET] (arXiv 2606.25605)

## 6. No-action / abstain calibration — idle-pass done right

- **Give an explicit THREE-way decision, not act/skip: {emit intent, no_action, need-more-evidence}.** Framing abstention as a first-class labeled outcome (not a fallback) sharply improves calibration in agent studies. [FLEET] (arXiv 2607.10059 "AgentAbstain"; arXiv 2604.04565 "PassiveQA" three-action framework)
- **Use a "verify-then-abstain" instruction: require the agent to CHECK for concrete triggers before acting, and to emit `no_action` if none are found.** Verify-then-abstain substantially raises correct-abstention rates. Concretely: "List the specific new facts/changes since last pass. If none, emit no_action." [FLEET] (arXiv 2605.07769 "Coding Agents Don't Know When to Act"; arXiv 2606.28733 "Agentic Abstention")
- **Reward verification, not output volume — say so in the prompt.** Agents "feel compelled to edit even after realizing nothing's wrong"; the fix is to explicitly value a correct no_action as a SUCCESS, not a wasted pass. Tell the agent that inventing marginal threads/links is a failure. [FLEET] (arXiv 2605.07769; arXiv 2606.19380)
- **Watch the over-abstention backlash — abstain calibration must be paired with a "don't be lazy" clause.** Verify-then-abstain can overshoot into refusing solvable work. Balance with: "If there IS a genuine new development, you MUST act — silence on real events is also a failure." Evaluate both false-emits and missed-events, never abstention alone. [FLEET] (arXiv 2607.10059; arXiv 2606.28733 — "abstention is not unconditionally beneficial")
- **Anchor the abstain decision to a concrete delta, not a vibe.** Give a checkable criterion ("has the canon changed in a way that affects MY domain since my last pass?"). Ambiguity/underspecification is the top driver of both over-acting and over-abstaining; a concrete trigger removes it. [FLEET] (arXiv 2607.10059; Anthropic "right altitude")

---
**Top 5 cross-cutting moves for all 8 agents:** (1) write the prompt as a role specialization layered on the harness base, not a standalone prompt; (2) push a lightweight index, pull prose just-in-time via grep/read, and forbid writing-from-summary; (3) require file:line citations in the output schema to structurally force the tool loop against the constraint tax; (4) order the prompt RESEARCH-then-EMIT with an explicit stop rule; (5) make `no_action` a first-class, verify-then-abstain outcome that's rewarded, balanced by a "don't miss real events" clause.
